# DSH 桌面端「去 Electron、原生化」可行性分析

> 版本：v1.0 · 2026-08-28
> 分析对象：DeepSeek Harness Desktop（当前 Electron 33 套壳 + 本地 Node 服务 + Web GUI）

---

## 0. 结论速览

| 问题 | 结论 |
|------|------|
| 是否可行 | **可行，但不是"重写 UI"，而是"换壳 + 换运行时"** |
| 推荐路径 | **Tauri 2.x 或 .NET 8 + WebView2 壳 + 内嵌 Node 运行时**（保留 Web GUI 与服务端插件） |
| 性能收益 | 包体 78MB→约 30-40MB；内存减少约 30-50%；启动加快 |
| 减少 bug | **不必然**。业务逻辑（插件/服务）不动则 bug 不变；壳层 bug 减少，但新增语言边界与打包复杂度 |
| 最大风险 | Cordis 插件动态加载机制（ESM + 运行时 node_modules + patch.yml 注入）无法进单文件打包 |
| 不建议 | 用原生控件重画整个 GUI（≈ 重写整个 DSH + 所有插件，成本 >10 倍，收益低） |

---

## 1. 现状架构解剖（决定改造边界的根基）

DSH 桌面端**不是传统 Electron 应用**，而是三层结构：

```
┌────────────────────────────────────────────────────┐
│ L1 桌面壳（Electron 33）                            │
│   窗口 / 托盘 / 单实例 / 自启 / 防崩溃 / 3090 桥     │  ← 唯一"可替换"的层
├────────────────────────────────────────────────────┤
│ L2 本地服务（Node.js + @deepseek-ai/dsh CLI）       │
│   Cordis 插件体系 / HTTP 3080 / 记忆/皮肤/人设等    │  ← 不能消失，只能"换运行方式"
├────────────────────────────────────────────────────┤
│ L3 Web GUI（浏览器渲染的 React UI + 插件客户端）     │  ← 换引擎=换浏览器内核
└────────────────────────────────────────────────────┘
```

### 1.1 三个硬约束（决定方案边界）

1. **插件是运行时动态加载的**：Cordis 插件以 ESM JS 存在 `~/.dsh/profiles/{web,node_modules}`，通过 `cordis.patch.yml` 注入启停（`disabled: true` 安全模式）。它们依赖 Node 的 `import`、文件系统、`process` 全局——**不能编译进单文件，必须保留真实 node_modules 目录**。
2. **GUI 是浏览器应用**：`dsh web` 输出 SPA（3080），Electron 只是开着窗户看它。任何方案都逃不开"渲染一个网页/本地服务"的宿命。
3. **运行时副本机制**：`~/.dsh/profiles/` 是与源码分离的运行副本，插件改动靠文件复制同步——这是 Node 生态的既有约束，与外壳无关。

### 1.2 当前成本实测

| 项 | 数值 | 说明 |
|---|---|---|
| 安装包 | **77.9 MB** | `DeepSeek Harness Desktop-0.1.2-setup.exe` |
| 解包目录 | **268 MB** | 含完整 Chromium |
| Electron 版本 | ^33.0.0 | 每实例常驻内存约 150-300MB |
| dsh 服务本体 | ~0.1 MB 源码 | 但依赖完整 Node + npx 缓存 + profiles |

## 2. 三条"原生化"路线对比

### 路线 A：WebView2 壳（推荐）—— 把 Chromium 换成系统内核

用 Rust（**Tauri 2.x**）或 C#（**.NET 8 + WebView2**）写壳，窗口加载 `http://127.0.0.1:3080`，系统进程监控 / 托盘 / 单实例 / 自启用原生 API 重写；Node 运行时内嵌随包分发。

- **渲染引擎**：系统 WebView2（Chromium 内核，Windows 10/11 自带）
- **保留**：L2 服务、L3 GUI、全部插件逻辑
- **重写**：L1 壳（约 2500 行 main.js 的等价物）

### 路线 B：Node 单文件化 + 原生壳（激进）

用 Node SEA（Single Executable Applications）或 pkg 把 dsh CLI 打成 exe，再配 WebView2 壳。

- **致命问题**：SEA/pkg 把 JS 打进二进制后，**插件动态加载（L2 的 Cordis + 运行时 node_modules）无法工作**——目录结构、ESM 动态 import、`disable: true` 注入全破坏。只适合纯静态 CLI。
- **结论**：此路不通，除非 DSH 官方提供打包版 API。

### 路线 C：原生控件重画 GUI（不推荐）

用 WinUI 3 / Qt / Flutter 重建记忆列表、皮肤切换、对话界面……

- **成本**：≥10 倍当前工作量，等于重写整个产品 + 移植每个插件 + 复刻皮肤系统
- **收益**：几乎为零——GUI 已是 Web 技术，重画不会更快（渲染内核没变）
- **结论**：仅当要彻底抛弃 Web 生态时考虑，本场景不成立。

### 路线 D：原地优化 Electron（务实兜底）

不换壳，用 electron fuses 关闭调试、去掉可剥离模块、压缩 asar、懒加载插件。

- 收益：包体可压到 ~60MB，内存省 10-20%
- 缺点：治标不治本，仍背 268MB 目录。

## 3. Electron vs WebView2 原生壳——技术对比

| 维度 | Electron（现状） | WebView2 + Tauri/.NET（目标） |
|---|---|---|
| **包体** | 78MB 安装包 / 268MB 解包 | 30-40MB 安装包 / 60-90MB 解包（省 Chromium） |
| **内存** | 150-300MB / 实例（Chromium 常驻） | 80-150MB / 实例（WebView2 多实例共享内核） |
| **启动** | 冷启动 2-5s（初始化 Chromium） | 冷启动 1-2s（系统内核已常驻） |
| **渲染引擎** | 捆绑 Chromium（版本固定） | 系统 WebView2（随 Windows/Edge 更新） |
| **性能瓶颈** | 与 WebView2 同为 Chromium 内核，**页面内 JS 性能几乎无差异** | 同左；差异仅在进程/内存开销 |
| **开发语言** | JS/TS 全栈 | 壳：Rust / C#；业务：仍是 JS |
| **插件生态** | Cordis/Node 插件原样跑 | Cordis/Node 插件原样跑（L2 不变） |
| **系统集成** | 社区生态大（tray/autoUpdater/单实例） | 成熟但更少（tauri-plugin-*/WPF 库） |
| **升级维护** | 跟 Electron 大版本迁移 | 跟 WebView2/壳语言版本，升级面更小 |
| **安全** | 捆绑内核 + Node 主进程权限 | 系统内核更新即安全补丁；壳层攻击面更小 |
| **分发** | electron-builder NSIS | NSIS/MSI + 壳语言打包器 |
| **webview 权限控制** | 精细（webContents/预加载） | 相对粗（WebView2 权限策略） |
| **防崩溃移植** | 现有 JS 实现（已完成） | 需用 Rust/C# 重写（等量代码，测试可复用） |

### 3.1 性能结论（诚实版）

- **页面内操作**（对话、记忆列表滚动、插件 UI）：**几乎无差异**——内核都是 Chromium。
- **应用级开销**（内存、启动、常驻）：**WebView2 明显更优**，这是收益的主要来源。
- **"减少 bug"**：业务 bug 不会自动消失（L2/L3 代码不动）；壳层 bug 面变小；但**新引入**语言边界、WebView2 兼容差异、打包/签名复杂度带来的新 bug 风险。

## 4. 推荐技术方案（路线 A 细化）

### 4.1 备选壳框架

| 框架 | 语言 | 优点 | 缺点 | 适配度 |
|---|---|---|---|---|
| **Tauri 2.x** | Rust | 包体最小、性能最好、插件生态成熟 | Rust 学习曲线、编译慢 | ⭐⭐⭐⭐⭐ |
| **.NET 8 + WebView2** | C# | 系统集成友好（托盘/自启/事件日志）、开发快 | 需要 .NET 运行时（可自包含→包体增大） | ⭐⭐⭐⭐ |
| **Wails 3** | Go | 简单、单二进制、WebView2 | 生态较新、托盘/通知库略糙 | ⭐⭐⭐ |

### 4.2 目标架构

```
DeepSeek Harness Native.exe（壳：Tauri/.NET）
  │
  ├─ 进程监控/托盘/单实例/自启/3090 桥/防崩溃   ← 原生实现（重写，逻辑同现有 main.js）
  │
  ├─ [include] runtime\node.exe + dsh 服务目录    ← 内嵌 Node 运行时（Launch4j 式旁挂）
  │     └─ spawn: node runtime\dsh\bin.js --profile web --port 3080
  │
  └─ WebView2 (系统) ──load──> http://127.0.0.1:3080
```

### 4.3 关键技术点

1. **内嵌 Node**：安装器把 `node.exe`（约 25MB）与 dsh 包放到 `安装目录\runtime\`；壳用 `CreateProcess`/`std::process`/`Process.Start` 拉起，保持 detached + 探活 —— **完整迁移现有防崩溃逻辑**（归因/退避/安全模式/熔断）。
2. **WebView2 固定版本策略**：指定 `--user-data-folder`、固定 WebView2 版本策略（`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`），避免用户 WebView2 过旧导致渲染不一致。
3. **与网页通信**：WebView2 `postMessage`/`AddHostObject` 替代 Electron IPC + 3090 桥（或保留 3090 HTTP 桥=改动最小）。
4. **单文件打包误会澄清**：壳可单文件，但 Node 服务与 profiles 目录**必须留在文件系统**（插件动态加载），所以最终是"安装目录 + 用户目录 .dsh"双目录模型——与现状一致。
5. **升级**：壳二进制替换 + dsh 服务目录热替换；`~/.dsh` 用户数据永不覆盖。

## 5. 实施步骤（分 4 个阶段）

### Phase 0 — POC 验证（1-2 周，不碰现有发布）
1. 用 Tauri 建最小壳，加载 `http://127.0.0.1:3080`，验证：窗口/托盘/单实例
2. **关键验证**：WebView2 下皮肤系统、记忆列表、图片识别、CSS 滤镜等渲染是否一致
3. 实测内存/启动对比（同机同会话）
   - 出口：若渲染差异可接受 → 继续；否则降级路线 D（Electron 优化）

### Phase 1 — 壳功能移植（2-3 周）
1. 迁移：托盘菜单、开机自启、窗口细节（标题/图标/最小化到托盘）
2. 迁移：**防崩溃体系**（spawn/退出归因/退避重启/自动安全模式/watchdog/熔断限流/健康探针）——逻辑照搬，语言重写
3. 迁移：3090 HTTP 桥（restart/health/open/reveal/dom）或改 WebView2 直连
4. 皮肤感知（读 patch.yml 换背景）
   - 验证：`test-anticrash-deep.js` 的 13 个场景在 Rust/C# 侧等价重写并全过

### Phase 2 — 运行时与分发（1-2 周）
1. 打包内嵌 node.exe + dsh 服务目录
2. 安装器（NSIS/MSI）：首装迁移 `~/.dsh` 初始化、设 PATH 无关、桌面快捷方式
3. 代码签名（Authenticode）——否则 SmartScreen 拦截
4. 离线兜底：首次无 npx 缓存时从内置目录起服务

### Phase 3 — 打磨与灰度（持续）
1. WebView2 兼容清单回归（每个插件 UI 过一遍）
2. 崩溃上报（Windows Error Reporting / sentry-native）
3. 性能压测：长会话、大记忆库、皮肤动画
4. 双版本并行：Electron 版保留 1 个发布周期，确认稳定后切换

## 6. 风险评估

| # | 风险 | 等级 | 影响 | 缓解 |
|---|------|------|------|------|
| R1 | **Cordis 插件动态加载与单文件化冲突** | 🔴 高 | 若强行打包 Node → 插件全挂 | **不动 L2**：Node 服务保持目录形式，只替换外壳 |
| R2 | WebView2 渲染差异（皮肤 CSS、动画、字体） | 🟠 中高 | 部分 UI 错位/走样 | Phase 0 POC 早验证；固定 WebView2 版本；CSS fallback |
| R3 | 防崩溃逻辑重写引入新 bug | 🟠 中 | 恢复能力退化 | 13 场景测试原样移植；灰度双版本 |
| R4 | 内嵌 Node 版本/路径兼容 | 🟠 中 | 服务起不来 | 安装器自校验；版本固定；fallback 到系统 node |
| R5 | 壳语言团队学习成本（Rust） | 🟡 中 | 进度慢 | 选 C#（如团队熟）或 Tauri 用 JS 侧胶水 |
| R6 | 代码签名 / SmartScreen | 🟡 中 | 用户被拦截 | 提前申请证书；或 electron 版先签名过渡 |
| R7 | 升级通道（服务目录替换） | 🟡 中 | 升级中断会话 | 参考现有 keepServerOnQuit；停服窗口最小化 |
| R8 | 生态缺口（个别 Electron 库无替代） | 🟢 低 | 功能缺失 | 当前功能清单逐项核对（tray/autoUpdater 均有替代） |

### 6.1 风险总评

- **总体可控**，前提是守住一个红线：**只换壳和内核，不碰 L2 服务与 L3 插件**。
- 唯一**不可逆风险**是误把 Node 服务塞进单文件（R1）——方案已明确避开。
- **最大不确定**是 UI 渲染一致性（R2），必须在 Phase 0 花小成本验证，再做后续投入。

## 7. 收益预期（供决策）

| 指标 | Electron 现状 | WebView2 原生壳 | 提升 |
|------|-------------|----------------|------|
| 安装包 | 77.9 MB | ≈ 30-40 MB | -50% |
| 常驻内存 | 150-300 MB | 80-150 MB | -30~50% |
| 冷启动 | 2-5 s | 1-2 s | -50% |
| 页面操作性能 | — | — | 基本持平（同内核） |
| 业务 bug 数量 | — | — | 不变化（业务代码不动） |
| 壳层维护面 | 大（捆绑 Chromium） | 小（系统内核 + 原生壳） | 改善 |

**最终建议**：
- 若目标是"变小、变省、启动快 + 壳更稳" → **走 Phase 0 POC，Tauri 2.x 优先，.NET 8 次选**；
- 若目标里包含"业务 bug 减少" → 方向不变，但预期要修正：**业务 bug 靠测试与防崩溃体系解决（已在做），换壳只解决壳层问题**；
- 若想最快见效 → 先做路线 D（Electron 瘦身）过渡，同时跑 POC。

*附：本分析基于 desktop/main.js（981+ 行，含防崩溃体系）、dsh 插件动态加载机制与打包产物实测。数据来源为本机实测。*
